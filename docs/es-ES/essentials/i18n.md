# Internacionalización

::: warning Aún sin publicar
La API de jugador `inputCharset` / `outputCharset` que describe esta página está prevista para `@infernus/core` `^0.16.0`. **Esa versión aún no está publicada y, por ahora, no hay planes de publicarla.** Mientras tanto, `0.15.x` y versiones anteriores mantienen un único `player.charset` que cubre ambos sentidos.
:::

La internacionalización en `Infernus` gira en torno a la **conversión de codificaciones de caracteres**, no a la traducción multilingüe. Aunque `$t` puede cubrir necesidades de traducción, lo esencial es garantizar el intercambio correcto de datos entre el servidor (UTF-8) y el cliente del jugador (codificaciones heredadas como `ISO-8859-1` o `GBK`). La mayoría de los servidores atienden una sola región, así que puede que no necesite varios idiomas — pero conviene entender la [internacionalización del jugador](#internacionalización-del-jugador) para evitar texto ilegible.

## Extensión de VSCode

[infernus-starter](https://github.com/dockfries/infernus-starter) incluye un archivo de recomendación de extensiones (`.vscode/extensions.json`). Se recomienda encarecidamente aceptar la instalación cuando VSCode la proponga, para poder ver los datos de internacionalización fácilmente durante el desarrollo.

`i18n-ally-custom-framework.yml` y `settings.json` ya vienen configurados para la extensión.

## Ejemplo

### Definición de paquetes de idioma

Los paquetes de idioma son archivos `.json`. Los datos se organizan con **claves en árbol**.

Las cadenas pueden contener marcadores `%s` para valores dinámicos.

#### Paquete de idioma chino

```json
{
  "server": {
    "running": "成功运行由 node.js 强力驱动的 omp 服务器",
    "connection": "连接信息: %s - %s : %s"
  }
}
```

#### Paquete de idioma inglés

```json
{
  "server": {
    "running": "Successfully running an omp server powered by node.js",
    "connection": "connection information: %s - %s : %s"
  }
}
```

### Instancia

Cree una instancia de I18n con `new I18n("clave del idioma predeterminado", paqueteDeIdioma)`.

Normalmente solo necesitará la función `$t`.

`$t("clave de traducción", [arreglo de marcadores], clave de idioma)` devuelve el texto traducido para el idioma indicado.

Si no hay marcadores, pase `null`, `undefined` o un arreglo vacío.

Si omite el tercer parámetro, se usa el idioma predeterminado.

```ts
import { I18n } from "@infernus/core";

// Paquetes de idioma JSON internacionalizados
import zh_CN from "./locales/zh_CN.json";
import en_US from "./locales/en_US.json";

const locales = {
  zh_CN,
  en_US,
};

export const { $t } = new I18n("en_US", locales);

console.log($t("server.running"));
console.log($t("server.connection", ["127.0.0.1", "8080", "123456"]));
console.log($t("server.connection", ["127.0.0.1", "8080", "123456"], "zh_CN"));
```

### Funciones de utilidad

La clase `I18n` también ofrece varios **métodos estáticos** útiles para convertir entre codificaciones:

- `encodeToBuf`
  - Convierte una cadena en un arreglo de bytes con la codificación indicada.
- `decodeFromBuf`
  - Convierte un arreglo de bytes en una cadena con la codificación indicada.
- `getValidStr`
  - Extrae la cadena válida de un arreglo de bytes: el primer byte `0` marca el final.
- `convertSpecialChar`
  - Remapea las letras latinas acentuadas a los bytes donde la fuente original de SA guarda sus glifos. Véase [Cómo funciona](#cómo-funciona).

## Internacionalización del jugador

Cada instancia de jugador tiene tres propiedades de internacionalización: `inputCharset`, `outputCharset` y `locale`. Valores predeterminados:

```ts
class Player {
  inputCharset = "ISO-8859-1";
  outputCharset = "ISO-8859-1";
  locale = "en_US";
}
```

Las dos codificaciones responden a preguntas distintas:

- **Entrada: lo que el jugador envía al servidor.** `inputCharset` es la codificación con la que el servidor decodifica los datos de ese jugador: nombre (`GetPlayerName`), chat (`OnText`), comandos (`OnPlayerCommandText`), entrada de diálogos (`OnDialogResponse`) y `gpci`.
- **Salida: lo que el servidor envía al jugador.** El servidor codifica el texto con `outputCharset` y el cliente del jugador lo decodifica con esa misma codificación: mensajes (`SendClientMessage`), mensajes privados (`SendPlayerMessageToPlayer`), diálogos (`ShowPlayerDialog`) y globos de chat (`SetPlayerChatBubble`).

Si la codificación de entrada es incorrecta, el servidor lee basura de ese jugador (nombres, chat, comandos); si la de salida es incorrecta, el jugador ve basura.

`SetPlayerName` también codifica con `inputCharset`, de modo que el nombre sobrevive intacto a un viaje de ida y vuelta por `GetPlayerName`.

Ambas usan `ISO-8859-1` por defecto porque el cliente original de SA habla una sola codificación heredada en ambos sentidos. Un mod de cliente no tiene por qué: puede redibujar la fuente para que el cliente espere UTF-8 en pantalla mientras el teclado, el IME o la entrada parcheada siguen produciendo bytes heredados, o al revés. Con un solo `charset` hay que elegir un lado y estropear el otro; con dos propiedades se describe el cliente que el jugador realmente ejecuta.

```ts
PlayerEvent.onConnect(({ player, next }) => {
  // mod de fuente que dibuja UTF-8, en un cliente que aún escribe GBK
  player.inputCharset = "gbk";
  player.outputCharset = "utf8";
  return next();
});
```

Al asignar cualquiera de las dos propiedades se dispara `OnPlayerCharsetChange`, que indica qué lado cambió:

```ts
PlayerEvent.onCharsetChange(({ player, newCharset, oldCharset, direction, next }) => {
  console.log(player.id, direction, oldCharset, "->", newCharset);
  return next();
});
```

`locale` elige el paquete de idioma; las dos codificaciones deciden si el texto llega intacto. Configúrelas antes de que el jugador lea el primer mensaje: `OnPlayerConnect` es el momento más temprano y, si sondea el cliente, hágalo justo después del sondeo. La región puede deducirse de la dirección IP; `inputCharset` se detecta pidiendo al jugador que escriba una cadena conocida y probando codificaciones candidatas hasta que los bytes decodificados coincidan. Ese intercambio solo mide la entrada: `outputCharset` depende del cliente que ejecute el jugador (original, un mod de fuente o un russifier).

::: tip Migrar desde `player.charset`
`player.charset` ya no existe. Para reproducir el comportamiento anterior, asigne las dos propiedades a la vez:

```ts
player.inputCharset = player.outputCharset = "ISO-8859-1";
```

`OnPlayerCharsetChange` (expuesto como `PlayerEvent.onCharsetChange`) recibe ahora un argumento `direction` que indica qué lado cambió.
:::

### supportAllNickname

::: tip
Por defecto, el servidor del juego solo permite letras, números y guiones bajos en los nombres de usuario.
:::

OMP ofrece nuevas API para habilitar o deshabilitar valores de byte concretos (0–255) en los nombres de usuario.

`GameMode.supportAllNickname()` **aprovecha estas API para permitir que se conecten todos los nombres internacionales, incluidos los caracteres chinos y otros nombres no ASCII.**

```ts
import { GameMode } from "@infernus/core";

GameMode.onInit(({ next }) => {
  GameMode.supportAllNickname();
  return next();
});
```

## Cómo funciona

:::warning
El intercambio bidireccional solo funciona si `inputCharset` y `outputCharset` coinciden con el cliente del jugador. Un valor incorrecto solo estropea su propio sentido; el otro sigue funcionando.
:::

`Infernus` usa `iconv-lite` para la conversión y `polyfill.amx` para interceptar las retrollamadas del `gamemode`, que llegan como arreglos de bytes decimales.

Las API de servidor a cliente codifican UTF-8 según `outputCharset`: `SendClientMessage`, `SendClientMessageToAll`, `SendPlayerMessageToPlayer`, `ShowPlayerDialog` y `SetPlayerChatBubble`, además de todo lo construido sobre ellas.

Las retrollamadas de cliente a servidor decodifican según `inputCharset`: `OnText`, `OnPlayerCommandText` y `OnDialogResponse`, junto con `GetPlayerName`, `SetPlayerName` y `gpci`.

::: tip
La conversión no inventa caracteres: lo que no existe en la codificación de destino llega como `?`. Es una limitación del cliente original de SA. Un cliente `ISO-8859-1` que recibe emojis o caracteres chinos mostrará texto ilegible por mucho que se configure el servidor.
:::

`GameText` y `TextDraw` toman otro camino: ignoran las dos codificaciones del jugador y codifican con el `charset` que se les pasa (`win1252` en `GameText` y `ISO-8859-1` en `TextDraw` por defecto). Después, el cliente elige el glifo de la textura de su fuente según el valor del byte (como un sprite CSS) en lugar de decodificar los bytes como texto.

Además, ambas API remapean las letras latinas acentuadas (`é`, `ñ`, `ü`…) cuando hace falta: la fuente original de SA guarda sus glifos en bytes reservados, no en su posición Latin-1, y `convertSpecialChar` los mueve allí. La opción `convertSpecialChars` controla el remapeo: vale `true` solo para las codificaciones de la fuente original (`win1252`, `cp1252` e `ISO-8859-1`), y `false` para otras como `utf8` o `cp1251`, donde estropearía los bytes. Pásela explícitamente para cambiarla:

```ts
new GameText("...", 3000, 3).forAll("cp1251", false);
new TextDraw({
  x: 10,
  y: 10,
  text: "Привет",
  charset: "cp1251",
  convertSpecialChars: false,
}).create();
```

El ruso funciona con el mismo mecanismo desde el otro lado: un russifier es un mod de localización rusa que el jugador instala en su **cliente**; redibuja la fuente del juego y coloca las letras cirílicas en las celdas que la fuente original reserva para caracteres latinos acentuados. [`@infernus/rustext`](../ecosystem) aporta la mitad del servidor: reescribe el texto saliente de las RPC de `GameText`, `TextDraw` y `Menu` para que los bytes cp1251 caigan en las celdas de ese mod. Pase `charset: "cp1251"` de forma explícita (los valores predeterminados de arriba convierten el cirílico en `?` antes de que el paquete pueda verlo) y ajuste el `RussifierType` al paquete que el jugador tenga realmente instalado, porque cada paquete coloca las letras de forma distinta (`SanLtd` es el valor predeterminado, junto con `OneC`, `Rush`, `MG` y otros). El paquete no incluye ningún recurso de russifier. `@infernus/rustext` reescribe esas RPC, así que con `cp1251` basta: el remapeo ya está desactivado por defecto para `cp1251`. El texto enviado a todos los jugadores (`GameText.forAll`) no lleva id de jugador y no se convierte.

La Edición Definitiva de SA usa UTF-8 internamente. Si OMP añade soporte en línea para ella en el futuro, no debería hacer falta ningún tratamiento adicional.

## Caracteres ilegibles en la terminal

Si encuentra caracteres ilegibles en la terminal al usar bibliotecas de registro como `pino.js`, pruebe una de las siguientes soluciones.

Para **PowerShell**, ejecute el siguiente comando (solo afecta a la sesión actual).

Para que el cambio sea permanente, añada el comando a su [$PROFILE](https://learn.microsoft.com/es-es/powershell/module/microsoft.powershell.core/about/about_profiles?view=powershell-7.4).

```powershell
$OutputEncoding = [Console]::InputEncoding = [Console]::OutputEncoding = New-Object System.Text.UTF8Encoding
```

Para **cmd**, use el siguiente comando para iniciar el servidor OMP:

```sh
cmd /c "chcp 65001 > nul & omp-server"
```

Estos comandos cambian la codificación de la terminal a UTF-8.

En otros entornos, busque la solución por su cuenta.
